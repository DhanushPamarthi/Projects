# PBM Ingestion Database Schema

Database: PostgreSQL 16  
Application mode: server Bronze/Silver integration  
Last reconciled with SQL and application queries: 2026-10-08

## Schema sources and deployment order

The current API uses the live server model, where Bronze and core Silver tables already exist. Apply the application-owned migrations in this order:

1. `db/server_integration.sql`
2. `db/bronze_to_silver_scheduler.sql`
3. `db/campaign_daily_scheduler.sql`
4. `db/transport_layer.sql`
5. `db/age_campaign.sql`
6. `db/pg_cron_end_to_end.sql`
7. `db/testiq_to_bronze_scheduler.sql` when the TestIQ handoff is required

`db/init.sql` is a separate clean-database POC schema mounted by `docker-compose.yml`. It contains UUID based `bronzebox.raw_file`, generalized Silver entities, and the original Gold campaign model. Those table shapes are retained for clean POC/test compatibility, but they are not the live `testiq.ingestion_load` and server Bronze/Silver model queried by the current API.

## Layer overview

| Schema | Ownership and purpose |
|---|---|
| `bronzebox` | Server owned append-only JSONB entity records grouped by `load_id` |
| `silverbox` | Server owned normalized PBM entities and ETL audits; application adds AutoFill and DNC fields/tables |
| `goldbox` | Campaign qualification, notification outbox, and prescription-refill outputs |
| `testiq` | Ingestion control, campaign configuration, scheduling, orchestration, and audit |
| `transport` | SMS, email, and voice delivery staging plus journey audit |

## Application data flow

```text
JSON/file queue
    -> testiq.ingestion_load
    -> bronzebox.<entity> JSONB rows
    -> silverbox.process_membership(load_id)
    -> silverbox.process_prescription(load_id)
    -> Silver member/prescription/contact entities
    -> campaign-specific Gold procedure
    -> goldbox.notification_outbox / goldbox.prescription_refill
    -> transport.sms | transport.email | transport.voice
```

## Live operational tables

### `testiq.ingestion_load`

Primary control row for one accepted ingestion batch.

| Column | Type | Null/default | Notes |
|---|---|---|---|
| `load_id` | text | primary key | Sequence value serialized as text |
| `event_id` | text | not null, unique | CloudEvent ID or deterministic TestIQ template ID |
| `correlation_id` | text | not null | Source correlation ID |
| `original_filename` | text | not null | Queued source filename |
| `sha256` | char(64) | nullable, unique | Content deduplication hash |
| `source_system` | text | nullable | Event source |
| `document_type` | text | not null | Event type or `testiq.bronze-templates.v1` |
| `document_version` | text | nullable | Usually `1.0` |
| `file_size_bytes` | bigint | default 0 | Source byte count |
| `status` | text | default `BRONZE_LOADED` | See status lifecycle below |
| `member_count` | integer | default 0 | Bronze membership rows expected |
| `prescription_count` | integer | default 0 | Bronze prescription rows expected |
| `attempt_count` | integer | default 0 | Promotion attempts |
| `last_attempt_at` | timestamptz | nullable | Most recent promotion attempt |
| `error_message` | text | nullable | Latest orchestration error |
| `created_at` | timestamptz | default `now()` | Load creation |
| `silver_completed_at` | timestamptz | nullable | Terminal Silver time |

Status constraint: `BRONZE_LOADED`, `SILVER_PROCESSING`, `COMPLETED`, `COMPLETED_WITH_ERRORS`, or `FAILED`.

Sequence: `testiq.ingestion_load_id_seq`, initialized at 10000.

### Bronze entity tables

The live server supplies these tables with the common ingestion shape `id`, `load_id`, `created_time`, and `data JSONB`:

- `bronzebox.membership`
- `bronzebox.prescription`
- `bronzebox.drug`
- `bronzebox.benefit`
- `bronzebox.claim`
- `bronzebox.medical_claim`
- `bronzebox.order`
- `bronzebox.product`

The API writes membership and prescription template batches directly. Pharmacy events can also produce the optional entities. Membership is processed before prescription because the prescription transform resolves the member surrogate key.

### Existing Gold refill tables extended by scheduling

The server supplies `goldbox.prescription_refill`, `goldbox.prescription_refill_etl_audit`, and `goldbox.prescription_refill_record_audit`.

The scheduler adds these lineage fields:

- `goldbox.prescription_refill`: `campaign_id`, `campaign_run_id`, `evaluation_date`
- `goldbox.prescription_refill_record_audit`: `campaign_run_id`, `evaluation_date`, `exclusion_reason`

The partial unique index on `(campaign_id, evaluation_date, prescription_sk, next_refill_date)` makes repeated campaign evaluation idempotent.

## Do-not-contact and Transport schema

### `silverbox.do_not_contact`

| Column | Type | Notes |
|---|---|---|
| `do_not_contact_id` | bigint identity | Primary key |
| `member_sk` | bigint | FK to Silver member |
| `channel` | text | `SMS`, `EMAIL`, `PHONE`, or `ALL` |
| `reason` | text | Optional exclusion reason |
| `effective_at` | timestamptz | Default now |
| `expires_at` | timestamptz | Nullable expiry |
| `active` | boolean | Default true |
| `created_at`, `updated_at` | timestamptz | Audit timestamps |

Unique key: `(member_sk, channel)`. Active lookup index: `(member_sk, channel, active)`.

### `transport.journey_run_audit`

One execution record per channel journey. It stores `journey_run_id`, `channel`, start/completion timestamps, status, selected/routed/DNC/missing-contact/duplicate/failed counts, and `error_message`.

### `transport.journey_processing`

Coordination row keyed by `gold_record_id`, with FKs to `goldbox.prescription_refill` and `silverbox.member`. It stores campaign, channel, processing status, attempt count, timestamps, and error data so concurrent workers cannot route the same Gold record twice.

### `transport.journey_record_audit`

Record-level evidence with FKs to journey run, Gold refill, and optional DNC record. It stores member/campaign/channel, masked destination, result code, detail, and created timestamp. Result codes include `ROUTED`, `DNC_EXCLUDED`, `MISSING_CONTACT`, `DUPLICATE`, and `FAILED`.

### Channel delivery tables

`transport.sms`, `transport.email`, and `transport.voice` each reference the Gold refill, Silver member, campaign, and journey run. They store the resolved destination, payload/message fields, delivery status, provider identifiers, attempt/error fields, and timestamps.

Each channel table has:

- an idempotency key tied to the Gold record;
- a pending-delivery index;
- an index on member and campaign;
- a channel-specific destination and content contract.

## Idempotency and concurrency

- Ingestion is deduplicated by `event_id`, SHA-256, queued file content, and queued payload equality.
- Bronze to Silver uses transaction advisory locks and processes only `BRONZE_LOADED` control rows.
- Membership runs before prescription for every load.
- Campaign creation uses a unique configuration fingerprint.
- Campaign daily work is unique per campaign and evaluation date.
- Notification snapshots are unique per campaign, member, prescription, and refill date.
- Transport uses a coordination record and channel-specific unique keys.
- Scheduled procedures use row locks/advisory locks, allowing pg_cron and backend fallback checks to overlap safely.

## Scheduler contract

PostgreSQL `pg_cron` is the primary scheduler. The application runs APScheduler fallbacks every five minutes when the corresponding pg_cron job is missing, stale, failed, or unreadable.

The three recurring stages are:

1. pending Bronze to Silver loads;
2. due Silver to Gold campaigns;
3. Gold to Transport channel journeys.

All campaign business-date logic uses `Asia/Kolkata`; service scheduling infrastructure runs in UTC where appropriate.
